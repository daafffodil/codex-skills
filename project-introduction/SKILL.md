# 项目介绍与思考逻辑

在任务产生实际成果时，把项目说明和用户的思考过程一起沉淀为可持续更新的 Markdown 文档。

## 自动触发

- 新任务产生文件、程序、设计、研究、方案、内容或其他实际交付时，在最终交付前自动使用本技能，不等待用户再次提醒。
- 同一项目继续修改时，同步更新两份已有文档，使它们反映最新需求和成果。
- 仅有寒暄、状态询问、澄清问题或尚未形成结果时不创建文档；形成交付后再补齐。
- 每次触发都必须同时生成或更新项目介绍与思考逻辑，不得只在对话中返回文字。

## 读取项目

1. 优先读取用户的原始需求、后续反馈、关键选择、项目说明和人工修改。
2. 项目文件可访问时，检查 README、核心产物、配置和已有两份文档；只读取完成任务所需的内容。
3. 不编造目标、数据、成果、角色、影响或用户没有表达过的想法。缺少信息但不影响主线时，使用最小必要表述。

## 产物一：项目介绍

默认严格使用以下结构：

```markdown
# {项目名称}项目介绍

## 需求

{一句话}

## 实现手段

{第一句话。第二句话。}

## 这个项目体现我的能力

{第一句话。第二句话。}
```

写作要求：

- “需求”用一句完整的话说明为谁解决什么问题，以及为什么需要这个项目，不加入方案细节。
- “实现手段”固定两句话：第一句说明项目主导者定义的问题、范围、结构、标准、流程或关键决策；第二句说明系统、工具、AI、自动化或协作方式如何执行，并形成什么可复用产物。
- “这个项目体现我的能力”固定两句话并使用第一人称：第一句只提炼一个最核心能力；第二句补充两至三个有事实支撑的能力。
- 不把“会使用 AI”本身当成核心价值；明确区分“人定义问题、标准和判断”与“AI 规模化执行”。
- 不堆砌技术名词，不使用“赋能、闭环、抓手、全链路升级”等空泛表达。

## 产物二：思考逻辑

默认使用以下结构，并根据证据多少保持简洁：

```markdown
# {项目名称}思考逻辑

## 最初的问题

{用户最开始感受到的阻力、缺口或机会。}

## 问题是怎样被拆开的

- {从模糊感受中识别出的具体问题。}
- {问题之间的因果关系或优先顺序。}

## 关键判断与取舍

- {用户明确提出的判断、约束、偏好及其原因。}

## 需求如何演化

1. {初始需求。}
2. {反馈带来的调整。}
3. {最终收敛的方向。}

## 最终形成的原则

- {可复用于后续工作的原则。}
```

记录要求：

- 只记录用户在需求、反馈和修改中可观察到的思考，不输出或声称输出助手的隐藏推理过程。
- 按“遇到什么问题 → 如何重新定义 → 做了什么取舍 → 形成什么标准”的因果顺序组织，不写聊天流水账。
- 优先保留“为什么”，同时写清被放弃的方案及原因；没有证据时不补写。
- 用户通过修改而非直接陈述表达偏好时，使用“从这次调整可以看出”等审慎措辞，避免把推断写成事实。
- 合并重复观点，保留真正改变项目方向的反馈。

## 保存与交付

- 默认把项目实际交付目录视为项目根目录；无法判断时使用当前工作目录。
- 保存为项目根目录下的 `{项目名称}项目介绍.md` 和 `{项目名称}思考逻辑.md`。
- 更新时直接编辑原文件，不创建“最终版”“新版”等副本。
- 若项目已有介绍或复盘文件，优先沿用其名称和结构，并补齐本技能要求的信息。
- 最终回复提供两份文件入口，并附一句适合向别人介绍该项目的核心定位。
